# Rust↔TS Seam Audit — SDK Portability Review

**Date:** 2026-09-26 · **Scope:** `js/src/` (TypeScript) vs `crates/betterbase-wasm` + `crates/betterbase-db-wasm` + core crates · **Motivation:** planned SDKs in other languages (Flutter/Dart, …)

## Purpose

Before building a second-language SDK, verify the partition principle:

> **All logic that must be identical across language SDKs — crypto, wire/serialization formats, protocol semantics, CRDT logic, key management — lives in Rust. The TS layer is idiomatic TS/JS ergonomics + platform glue (Web APIs, React, events, storage backends).**

If the principle is violated, a Dart SDK author would be forced to port from _TypeScript source_ — and each port is a fresh chance for silent divergence on frozen v1 contracts.

## Method

Five parallel domain audits (crypto, auth, db, sync-protocol, file-store/space-manager), each classifying every TS module as:

- **WRAP** — thin passthrough to a wasm function (fine)
- **SHOULD-BE-RUST** — TS re-implements what is (or should be) a Rust core function (flag)
- **PLATFORM** — browser-platform glue each language SDK reimplements naturally (fine, note)
- **TS-ERGO** — typing/caching/ergonomics layered over wasm (fine, note if substantial)

## Overall verdict

**The seam was inverted for exactly the code the principle targets.** Primitive crypto (AES-GCM v4, HKDF, DEK wrap, P-256 signing, canonical JSON, edit chains, JWE) is properly Rust and the TS wrappers are exemplary. The composite protocol logic — the frozen v1 contracts and protocol state machines — started life in TS, in two flavors; per-domain status below reflects the wiring done since (2026-09-26/28):

1. **Dead Rust twins** — Rust implementations exist, are exported via wasm, and are _never called_; TS re-implements them alongside. **Mostly wired since the audit (2026-09-26/28):** the sync.rs composites (frames, envelope v4, pull assembly) and the membership fold are now canonical and live, and the file-store policy surface (claimability, stale window, queue transitions, eviction, migration planning, re-key apply) is wired. Still dead: the five membership entry-construction exports (parse/serialize/build/encrypt/decrypt — TS twins do the construction; only the _fold_ is canonical in Rust, G4), and `next_claim_batch`/`apply_re_key` in the file-store core (retained for SDKs with keys up front / a storage-touching apply the TS shell does inline). The remaining Rust core is no longer a shadow canon — it is the canon, with a small quarantined tail.
2. **No Rust at all** — logic with no Rust counterpart, so a second SDK would port from TypeScript (push-policy conflict handling, `transferUnuploadedFrom`, spaceid derivation, `__spaces` schema constants, session-key separation).

### Root cause

The wasm surface froze before AUD-024/025/026 and the CryptoKey path. Rather than extending Rust, TS absorbed the new protocol semantics locally. Nothing caught it: **there was no CI check that every wasm export has a TS call site** — the dead surface proved the check was missing. **Resolved (2026-09-27):** `js/scripts/check-wasm-exports.mjs` (run as `pnpm check:wasm-exports`; part of `pnpm check` and a CI step in `.github/workflows/check.yml`) parses the generated `pkg/*.d.ts` surface and fails on any function export with no call site in `src/`/`browser-tests/` unless suppressed with a reason. Liveness is a word-boundary textual check (comments/strings stripped): dead exports are tracked in a `DEAD_WITH_PLAN` table (stale-checked — it must shrink as the surface is wired up) and exports whose names collide with unrelated live TS identifiers in a `NAME_COLLISIONS` table.

**Gap list:**

1. **Sync orchestration policy — Rust mirror exists, is dead, and already drifted** [Critical → RESOLVED by design decision (D5, 2026-09-27)]. TS owns the push policy (`pushWithConflictRetry`, bisection isolation, `classifyPushRejection`, per-collection `deleteStrategy`) and the Rust mirror (`betterbase-db::sync`) had none of the four, was unreachable from any product (`JsSyncTransport` `#[allow(dead_code)]`), and its passing test suite made the incomplete behavior look authoritative. **Decision: quarantine.** The mirror is **deleted** (`src/sync/`, `tests/sync/`, db-wasm `sync.rs`, tokio deps), the TS coordinator stands as the reference implementation, and the cross-SDK invariants it encodes are pinned by a freeze doc (`docs/sync-push-policy.md`, six invariants + flip triggers) and a Rust-canonical classification table (`betterbase-sync-core::push_policy`, pinned by `test-vectors/push-rejection.json`). A full machine port (rotation-style event-driven `PushPolicy` driven by a TS I/O host) is deferred until a flip trigger fires — funded/dated second SDK, non-browser consumer of `betterbase-db`, or an observed cross-SDK divergence.
2. **`merge-records.ts` — classified by regex over Rust error strings** [Critical → RESOLVED (code-based)]. Disposition was matched on `/unique/i` (:172) and `/\b(deleted|not found|unique)\b/i` (:217) against `error.rs:67-81` wordings, so a reworded Rust error silently changed adoption behavior. **Fixed:** the engine now emits a frozen `code` on every thrown error and per-record `RecordError` (`LessDbError::code`); the merge classifies on `DbErrorCode` and fails loudly on any missing/unrecognized code. Remaining (not the danger): the merge _policy itself_ (`mergeRecordFields` :261, `unionArrays` :308) still lives in TS — a future `adopt_records` engine call could take it into Rust, but the policy is a TS-ergonomics decision, not a cross-language invariant.
3. **Middleware adapter semantics exist twice as live-quality code** [Important]. Nothing in `js/src` references `WasmTypedDb`; the live path runs the TS re-implementation. Route through `WasmTypedDb`, or bless the TS adapter as "host-language hook runner" and strip the Rust mirror.
4. **`SyncScheduler` duplication** [Important → RESOLVED (D5)] — the Rust `sync/scheduler.rs` twin was deleted with the sync mirror; the TS scheduler stays as client choreography (gap 1).
5. **Cross-language wire conventions maintained by implicit agreement** [Important] — canonical-rep edge cases (dates in unions never convert back, untyped Date→string, `undefined`-stripping vs `strip_null_optionals`) enforced only by separate per-language unit tests. Fix: golden vector tests (TS write→Rust read byte-identical) + generate TS wire types from Rust serde (ts-rs/typify).
6. **Stringly-typed server-protocol codes at the seam** [Suggestion → half-resolved (D5)] — the rejection-code → disposition table is now Rust-canonical (`push_policy::classify_push_rejection`) and vector-pinned; `mapDeleteStrategy` still silently drops unknown strategies in TS (client-side delete-policy mapping, not a server contract — deferred).
7. **Rust builder `panic!`s on reserved fields** [Suggestion] — `collection/builder.rs:451` traps where it should return `Err` (a Dart SDK hitting `build()` directly gets a wasm trap).

2. **Envelope v4 pipeline duplicated; Rust twin dead and stale** [Critical — **Resolved (2026-09-27)**]. `betterbase-sync-core::transport` is now the canonical pipeline: `encrypt_record`/`decrypt_record` take the caller-resolved epoch KEK (the key-resolution ladder stays a platform concern via `selectEpochKey`, see G2) and run CBOR → pad → fresh-DEK AES-256-GCM (AAD bound to spaceId+recordId) → AES-KW wrap end-to-end in Rust, with `encode_envelope`/`decode_envelope` as the canonical CBOR codec. `epoch_cache.rs` (the epoch-pinning `EpochKeyCache`) was deleted — its only consumer was the dead Rust twin; `rewrap_deks` still precomputes its own inline epoch-key ladder over the whole advance (now bounded by `MAX_EPOCH_DERIVE_DISTANCE`, the same cap as `select_epoch_key`). Conformance pinned by `test-vectors/envelope-pipeline.json` (envelope CBOR, padding, AAD layout, deterministic AES-KW wrap, golden end-to-end blob with AAD tamper checks): Rust `vectors_*` tests + `browser-tests/sync/envelope-pipeline.test.ts` (real wasm); node unit tests run a 1:1 JS mirror (`transport-mock.ts`, never executes wasm); the CI guard promoted the pipeline exports from `DEAD_WITH_PLAN` to live.
3. **Pull chunk-assembly in TS** [Critical — **Resolved (2026-09-27)**]. `betterbase-sync-core::pull` is now the canonical state machine: `PullAssembly` (per-space prev/cursor/epoch/rewrap/received) with a single `apply_chunk` entry point. Wasm surface: `pullAssemblyApply` (state object in/out — the host decodes the chunk's CBOR `data` into a plain object (cborg: byte strings → `Uint8Array`); the TS hot path passes only the pruned protocol fields so payload bytes never cross the wasm boundary, and the binding converts the object back to CBOR (`Uint8Array` → byte string) so the canonical byte path runs verbatim) and `pullAssemblyResult` (client-facing names, spaces sorted, `rewrapEpoch` omitted when absent). Entry payloads (Uint8Array blobs) stay in the TS shell — `WSClient.pull` buckets them per space alongside the reducer. Conformance pinned by `test-vectors/pull-assembly.json` (22 cases, incl. real wire-shape CBOR byte-string payloads): Rust vector suite, `js/src/sync/pull-assembly.test.ts` (node, 1:1 mirror `pull-assembly-mock.ts`), and `browser-tests/sync/pull-assembly.test.ts` (real wasm).

- **G1. Upload-queue state machine: TS live, Rust canon unwired** [Critical, **resolved by design decision + wiring (2026-09-26, D3/D4)**]. The shape divergence (TS claims lazily one-at-a-time gated on `getUploadKey()`; Rust claimed the whole batch upfront with no upload-key concept, design-doc `KeySource` unbuilt) is resolved by the D4 design decision: the lazy, key-gated claim loop **stays in the TS shell** (a batch-upfront claim would pin entries as `uploading` for up to the stale window when the space's upload key is not yet available); the Rust core owns everything the batch shape _was_ encoding. Residuals: `next_claim_batch` stays in the core for SDKs with keys up front; `transferUnuploadedFrom`'s transfer mechanics remain TS (G6).
- **G2. Epoch-key selection ladder: three copies, canonical one unused** [Critical, resolved 2026-09-26]. TS-local `MAX_EPOCH_ADVANCE` literals deleted (transport.ts, reencrypt.ts — reencrypt's raw path is now bounded too); the bound is Rust's constant via `maxEpochDeriveDistance()`. Only the CryptoKey (non-extractable WebCrypto) path keeps an in-TS HKDF chain, checked against the same Rust-provided cap. Frozen contract: transient share failure PROPAGATES (retryable); only a definitive no-share (null) falls through.
- **G3. Key-rotation orchestration exists only in TS** [Critical — **resolved (2026-09-27, T12)**]. The rotation state machine is now canonical in Rust: `betterbase-sync-core::rotation` (`crates/betterbase-sync-core/src/rotation.rs`) — a pure, event-driven machine (no I/O, no async, no clock) with 16 actions × 4 events (`actionSucceeded` / `shareResult` / `advanceConflict` / `actionFailed`) and four run kinds (scheduled / removal / interrupted / adopt) composed over a frame stack: conflict-completion and D-005 fresh re-rotations stack as parent–child frames, so the crash-safety ordering (fresh-key shares distributed *before* any DEK rewrap), the bounded removal-retry ladder (retry once, then a loud "revocation advance failed after retry" — revocation is already server-committed by then), and the D-005 give-up bound (one follow-up per conflict, one deferred pass, then give up with a `console.error`) are enforced by the machine rather than by call-site discipline. Wasm: `rotationStart`/`rotationStep`/`rotationAbort` (state is an opaque JSON value — in memory per space for the page session; a reload starts clean, which is safe because D-005 is best-effort) plus `shouldRotateSpaceEpoch` for the due-rotation policy (G7's `shouldRotateSpace` is now the Rust `should_rotate`; the interval constant is passed from TS and remains the seam to close). The host driver (`space-manager.ts`: `startRotation`/`driveRotation`/`executeRotationStep`) performs each action's I/O and reports outcomes; host failures on a D-005 follow-up are contained (the machine discards the follow-up frame and the host logs — matching the pre-port `runFreshFollowup` semantics), while any other failure aborts the run. `doRemoveMember` is now fold-under-lock + `runRotation`: the double UCAN revocation and the fold/rotation interleaving are gone, and "Member revoked but rotation did not complete" wraps only failures *after* the revocation committed. - **G4.
